# Capacity and Recovery Rehearsal Report, 2026-09-24

## 1. Storage Capacity Assessment

- **Host Environment**: Linux host `/dev/sda2` with 1.8 TiB total filesystem capacity, 22 GB currently in use, and ~1.7 TiB free space.
- **Acquisition Load**: 4 channels × 2,000 samples/sec/channel = 8,000 samples/sec = 691.2M samples/day (20.736 billion samples per 30-day retention window).
- **Filesystem Reserve**: 20% reserved capacity on 1.8 TiB = ~360 GB reserved.
- **Local Spool Buffer**:
  - Configured capacity: 128 GiB (`SPOOL_MAX_BYTES = 137438953472`).
  - Storage location: Dedicated persistent Docker volume `daq_spool` (`/var/lib/daq_navi/spool`).
  - Payload compression: SQLite format with zlib level 1 compression per batch.
  - Measured buffer consumption: 4.42 GB / 24 hours at quiet baseline (~6.4 bytes/sample), scaling to at most ~17.3 GB / 24 hours under high-entropy signal noise (~25 bytes/sample). SQLite WAL and gap metadata consume < 1 GB.
  - Conclusion: 128 GiB spool provides 7+ days of buffering capacity, exceeding the required 24-hour continuous outage buffer by >7x.
- **TimescaleDB Rolling Raw Retention**:
  - Hot uncompressed chunk (1 day): 691.2M samples × 374 bytes/sample (table + B-tree indexes) = ~258.5 GB.
  - Compressed historical chunks (29 days): Compressed by channel (`segmentby='channel'`, `orderby='time_ns DESC'`). Measured at 16 bytes/sample (~11 GB/day), conservative upper bound at 30 bytes/sample (~20.7 GB/day) = ~320 GB to ~600 GB for 29 days.
  - Total 30-day storage requirement: ~578 GB to ~858 GB.
  - Total requirement including 128 GiB spool + 360 GB reserve: ~1,066 GB to ~1,346 GB, safely within the 1.8 TB drive (~1,700 GB available).
  - TimescaleDB retention policy: Set to 30 days via `add_retention_policy('daq_production_samples', INTERVAL '30 days')`, configurable live through the web UI and `/api/retention`.

## 2. Recovery Rehearsals via Web UI & API

All operator and failure scenarios were exercised end-to-end against the web UI API with isolated test tables in TimescaleDB (`daq_navi_test_4a287a5e26`):

1. **Standard Acquisition & Clean Stop Workflow** (`web-f0e9a0923d.json`):
   - Started 4-channel production acquisition via `/api/start`.
   - Verified balanced channel sample rates across channels 0–3 (10,000 samples per channel).
   - Sample visualization query `/api/samples` returned HTTP 200 with raw voltage, calibrated values, units, and calibration revisions.
   - Clean `/api/stop` drained the pipeline; `pending_replay` returned `false` and status transitioned to `stopped`.

2. **Database Outage and Spool Replay** (`web-replay-0a20659afc.json`):
   - Simulated database outage by redirecting `DB_DSN` to an unreachable port during active acquisition.
   - Pipeline transitioned into `buffering` state, recording writer failures in runtime status while continuing uninterrupted physical sample collection in the local SQLite spool (`pending_batches` accumulated).
   - Restored valid database destination: spool drain thread automatically replayed accumulated batches into TimescaleDB.
   - Verified zero data loss and zero duplicate records (`count(*) == count(distinct sample_id)`).

3. **Child Process Crash & Recovery** (`web-faults-97a2f4caf8.json`):
   - Terminated acquisition child process ungracefully with `SIGKILL`.
   - Web runtime detected exited PID: `/api/status` reported `status: faulted` with `fault: acquisition_process_exited`, and `/api/health` returned HTTP 503.
   - Automatic gap recorded for the disruption period.
   - Calling `/api/start` successfully recovered acquisition, drained committed batches from the spool, and resumed ingestion.

4. **Hardware DAQ Error Handling** (`web-faults-97a2f4caf8.json`):
   - Started acquisition with non-existent DAQ device configuration.
   - System immediately transitioned to `status: faulted` with Advantech driver error `0xE0000015`; `/api/health` returned HTTP 503.
   - Verified strict isolation: No implicit mockup fallback occurred.

5. **Spool Buffer Exhaustion Drill** (`web-faults-97a2f4caf8.json`):
   - Configured buffer limit to force buffer exhaustion (`SPOOL_MAX_BYTES = 1`).
   - Acquisition halted physical capture immediately upon buffer saturation, marked `status: faulted`, returned HTTP 503 on `/api/health`, and recorded an acquisition gap with `cause: buffer_full`.

6. **Reboot and Auto-Start**:
   - Web application checks `AUTO_START_ON_STARTUP` and `AUTO_START_MODE` on startup.
   - Tested that auto-start resumes production acquisition on startup even if an operator previously issued a manual stop.

7. **Explicit Mockup Mode Separation** (`web-faults-97a2f4caf8.json`):
   - Mockup mode requires explicit selection (`mode: 'mockup'`).
   - Mockup telemetry writes exclusively to `DB_MOCKUP_TABLE` (`web_mockup_97a2f4caf8`), preserving complete separation from production table (`web_faults_97a2f4caf8`).

## 3. Real Deployment Verification

- Docker volume `daq_spool` is configured in `docker-compose.yml` mounted at `/var/lib/daq_navi/spool`, ensuring persistence across container restarts and upgrades.
- Production and mockup tables are cleanly segregated (`daq_production_samples` vs `daq_mockup_samples`).
- All storage parameters and recovery mechanisms satisfy the operational requirements for production cutover.
